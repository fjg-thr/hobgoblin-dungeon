# Cursor Bugbot Review Guide

Use this guide when reviewing pull requests for the Hobgoblin Ruin Prototype.

## Project context

- This is a Next.js App Router project that hosts a browser-only Phaser 4 game.
- The React shell lives in `src/app`; the Phaser bootstrapping code is in `src/game/GameCanvas.tsx`.
- Most gameplay logic is concentrated in `src/game/scenes/DungeonScene.ts`.
- Asset keys and paths are declared in `src/game/assets/manifest.ts` and must stay in sync with files under `public/assets`.
- Asset generation and processing scripts live under both `tools/` and `scripts/`.

## Review priorities

1. **Client/server boundaries**
   - Keep Phaser and browser APIs out of server-rendered modules.
   - Check that game boot code remains behind `"use client"` and dynamic imports where appropriate.
   - Avoid introducing module-level `window`, `document`, canvas, audio, or Phaser side effects.

2. **Phaser lifecycle and cleanup**
   - Verify scenes, timers, input handlers, tweens, sounds, and event listeners are cleaned up or owned by Phaser systems.
   - Watch for duplicate game instances, stale refs, or long-lived callbacks after React unmounts.
   - Treat asset preload keys, animation keys, and registry/data keys as shared contracts.

3. **Gameplay invariants**
   - Preserve movement, camera follow, collision, finite ammo, health, enemy spawning, pickup effects, scoring, mute state, and debug overlay behavior unless the PR explicitly changes them.
   - Flag changes that can make enemies, pickups, projectiles, damage state, or run timers leak between runs.
   - Smoke-test keyboard and pointer interactions. Current code binds staff-bolt firing to `Space` and pointer clicks; README text also mentions `J`, so flag changes that widen or preserve that mismatch without implementing it.
   - Keep seeker ammo behavior intentional: current code unlocks seeker pickups/projectiles after the configured kill or survival-time threshold, even though README gameplay docs focus on standard ammo.
   - Treat README/code differences around blast timing as existing context unless the PR intentionally fixes them; current code unlocks blast earlier than the README's "late rare power-up" phrasing implies.

4. **Assets and generated content**
   - Ensure manifest entries match committed files and metadata dimensions.
   - Verify generated spritesheets, JSON metadata, and audio manifests are committed together when referenced.
   - Keep generated source assets and generator/processor tooling references consistent when asset pipelines change.
   - Do not require hand-polished art or richer Foley beyond the README's known limitations.

5. **Next.js metadata and deployment**
   - Keep `metadataBase`, OpenGraph, and Twitter image paths valid for both local development and hosted deployments.
   - Check consistency between metadata references, share-image files such as `public/opengraph-image.png`, and any deployment-specific URL changes.
   - Avoid adding server-only assumptions that break static or Vercel-style deployments.

## Verification expectations

Ask authors to run the checks that match their change:

```bash
npm ci
npm run build
npx tsc --noEmit --incremental false
```

`npm run lint` currently points at `next lint`, but this repository does not include a dedicated ESLint setup and Next.js 16 treats `next lint` as a project-directory argument. Do not block a review solely because lint is unavailable unless the PR also fixes the lint script.

For gameplay changes, also ask for a short manual smoke test covering start screen, movement, aiming/firing with `Space` and click, enemy contact damage, ammo and power-up pickups, mute toggle, game over, and restart.

## Known repository notes

- `npm ci` may report existing audit warnings, currently including one moderate and one high vulnerability. Mention dependency risk only when a PR changes dependencies or materially changes the audit output.
- `next-env.d.ts` can be regenerated by Next.js build tooling. Avoid treating generated churn in that file as meaningful unless it reflects a real framework or TypeScript change.
- The README documents intentional prototype limitations. Do not file review comments that only restate those limitations.
- Managed Cursor Bugbot enablement is controlled outside the repository through Cursor dashboard/GitHub App settings; this file provides repository-specific review guidance once Bugbot is enabled.

## Review output style

- Prefer concrete, reproducible findings tied to changed lines.
- Include why the issue matters in this game's runtime behavior.
- Separate blockers from optional improvements.
- Avoid broad refactor requests unless they are necessary to fix a specific defect introduced by the PR.
