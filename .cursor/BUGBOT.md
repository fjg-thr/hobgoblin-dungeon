# Cursor Bugbot Review Instructions

Use these repository-specific instructions when reviewing pull requests for the
Hobgoblin Ruin Prototype.

## Project context

- This is a Next.js App Router project with a client-only Phaser game mounted
  from `src/game/GameCanvas.tsx`.
- Most gameplay lives in `src/game/scenes/DungeonScene.ts`; changes there often
  affect rendering, input handling, combat, collision, spawning, audio, and
  performance in the main update loop.
- Runtime assets are served from `public/assets/**` and referenced through
  `src/game/assets/manifest.ts`. Several assets are generated by scripts in
  `tools/` and `scripts/`.

## Review priorities

1. Catch browser/server boundary regressions.
   - Phaser imports should stay client-only; avoid direct Phaser usage from
     server components.
   - React effects that create a `Phaser.Game` must clean it up on unmount and
     avoid duplicate game instances during remounts.

2. Check game-loop correctness.
   - Verify time-step changes keep `MAX_SIMULATION_DT` style clamping intact.
   - Look for unbounded allocations, timer buildup, event listener leaks, and
     animation or texture keys that can be registered repeatedly.
   - Confirm pooled visual effects, projectiles, pickups, and enemies are
     marked inactive or destroyed consistently.

3. Protect gameplay invariants.
   - Tile/world coordinate conversions should remain consistent with
     `HALF_TILE_WIDTH`, `HALF_TILE_HEIGHT`, and map offsets.
   - Collision, spawn safety, enemy pathing, pickup radius checks, and projectile
     hitboxes should be reviewed together when any one of them changes.
   - Difficulty, ammo, health, power-up, score, and game-over changes should not
     create unwinnable starts, infinite resource loops, or unreachable pickups.

4. Validate asset references.
   - New manifest entries should point to committed files under `public/assets`.
   - Sprite frame dimensions, frame counts, metadata paths, and animation row
     assumptions should match the actual sheet JSON or image layout.
   - Generated asset changes should not introduce network/runtime dependencies.

5. Preserve player-facing controls and feedback.
   - Keyboard, pointer, fire, sound toggle, debug overlay, start screen, game
     over, restart, and pickup feedback should keep working after related
     changes.
   - For UI or CSS changes, preserve full-viewport canvas sizing, pixelated
     rendering, and dark GBA-inspired presentation.

## Expected verification

- For TypeScript, gameplay, asset manifest, or app-shell changes, expect
  `npm run build` to pass.
- For gameplay or UI changes, expect a manual browser playthrough covering:
  start, movement, aiming/firing, ammo pickup, power-up pickup, enemy damage,
  player damage/game over, restart, and sound toggle.
- For generated assets or tooling changes, expect the relevant `npm run
  process:*` or `npm run generate:*` command to be run when practical, plus a
  build or browser smoke test that loads the changed assets.

## Noise guidance

- Do not focus review comments on large binary asset diffs unless the change
  breaks manifest references, dimensions, file size expectations, or runtime
  loading.
- Prefer actionable findings with concrete reproduction or verification steps.
