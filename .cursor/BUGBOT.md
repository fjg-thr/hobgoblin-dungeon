# Cursor Bugbot Review Guidance

Use this repository-specific guidance when reviewing pull requests for the Hobgoblin Ruin prototype.

## Project context

- This is a Next.js App Router project that hosts a Phaser 4 RC game in a client-only React component.
- The main game loop, state, combat, enemy behavior, collision, UI overlays, and audio live in `src/game/scenes/DungeonScene.ts`.
- The fullscreen game canvas is mounted from `src/app/page.tsx` through `src/game/GameCanvas.tsx`, which dynamically imports Phaser and the game scene on the client.
- Dungeon generation and tile semantics live in `src/game/maps/startingDungeon.ts`.
- Runtime asset paths, sprite sheet dimensions, audio keys, and manifest metadata live in `src/game/assets/manifest.ts`.
- Generated and processed game assets are stored under `public/assets/**`; source prompts are documented in `ASSET_PROMPTS.md`.

## Review priorities

1. **Gameplay regressions**
   - Check player movement, aim snapping, firing, ammo consumption, enemy spawning, contact damage, power-ups, heart pickups, scoring, game-over/restart flow, mute state, and debug overlay behavior.
   - Watch for coordinate-space mistakes between tile, world, camera, pointer, and screen values.
   - Verify collision changes keep wall, prop, projectile, pickup, and enemy interactions consistent with the isometric map.
   - Review Phaser object lifecycle changes for leaked timers, tweens, input handlers, sounds, or game objects after restart or scene shutdown.

2. **Next.js and React boundaries**
   - Keep Phaser and browser-only APIs inside client-side code paths. Server components, metadata, and configuration should not depend on `window`, `document`, or Phaser runtime imports.
   - Preserve the dynamic client boot pattern in `GameCanvas.tsx` unless a change deliberately replaces it.
   - For metadata changes in `src/app/layout.tsx`, verify referenced OpenGraph/Twitter image paths exist in `public/` or are otherwise generated by Next.js.

3. **Asset and manifest integrity**
   - When asset files change, verify the corresponding manifest entries, frame dimensions, JSON metadata, README asset list, and processing scripts still agree.
   - Review changes under `public/assets/**` together with related updates in `src/game/assets/manifest.ts`, `ASSET_PROMPTS.md`, `tools/`, `scripts/`, and `package.json`.
   - Be strict about path casing and leading slashes because Phaser loads assets from public URLs.
   - For generated sheets, check transparent backgrounds, nearest-neighbor/pixel-art assumptions, frame counts, and dimensions used by animations.

4. **TypeScript and maintainability**
   - Keep strict TypeScript types; avoid broad `any`, stringly typed asset keys, or unchecked casts when local types can express the invariant.
   - Prefer focused helpers for deterministic logic such as map generation, collision, enemy targeting, and scoring rules.
   - Avoid unrelated refactors in the large scene file unless they directly reduce risk in the changed behavior.

5. **User-facing quality**
   - Preserve keyboard controls, mouse controls, full-window resize behavior, pixel-art rendering, readable overlays, and the scene-level audio mute toggle.
   - If UI controls are added outside Phaser, require accessible labels and keyboard operation.
   - Keep performance-sensitive work out of per-frame update loops unless it is bounded and necessary.

## Verification expectations

Ask authors to run the most relevant subset of these checks for their change:

```bash
npm ci
npm run build
npx tsc --noEmit --incremental false
```

For gameplay or rendering changes, also request a local smoke test:

```bash
npm run dev
```

Open `http://localhost:3000` and verify movement, firing, pickups, damage, game over, restart, resize, and mute behavior touched by the change.

For asset-pipeline changes, request the specific affected script, for example:

```bash
npm run process:assets
npm run process:death-assets
npm run process:combat-juice
npm run generate:powerups
npm run generate:combat-assets
```

The current `npm run lint` script invokes `next lint`, which is not available in the lockfile-resolved Next.js 16 CLI. Do not treat that lint command as a required blocker until the project migrates to a supported ESLint command or configuration.

## Review style

- Lead with concrete correctness issues, regressions, missing verification, and asset mismatches.
- Include file and line references when possible.
- Do not request broad rewrites, dependency swaps, or new frameworks unless the diff introduces a clear risk that requires them.
- If a change is safe but lacks an automated test target, ask for precise manual verification steps instead of generic "add tests" feedback.
