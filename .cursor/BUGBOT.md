# Cursor Bugbot Review Guidance

Use these notes when reviewing pull requests for `fjg-thr/hobgoblin-dungeon`.

## Deployment and service boundary

- This file supplies repository-specific review context for Cursor Bugbot.
- It does not prove that the hosted Bugbot service is enabled. Confirm service
  deployment through Cursor dashboard/org settings, GitHub App repository access,
  Admin API credentials/configuration when those are used, and a live PR smoke
  review after this file is merged to the default branch.
- Manual smoke triggers supported by Cursor public Bugbot docs include top-level
  PR comments with `cursor review` or `bugbot run`. For diagnostics, use
  `cursor review verbose=true` or `bugbot run verbose=true` and capture the
  request ID or verbose log details.
- Rules in this file apply after `.cursor/BUGBOT.md` lands on the default
  branch. A PR adding or changing this file may not be reviewed with the new
  guidance yet.

## Project shape

- Next.js App Router app with React and TypeScript.
- The playable game is a Phaser canvas mounted by `src/game/GameCanvas.tsx`.
- Core gameplay, UI overlays, input, enemy progression, pickups, audio, and
  cleanup live primarily in `src/game/scenes/DungeonScene.ts`.
- Dungeon layout data lives in `src/game/maps/startingDungeon.ts`.
- Runtime asset loading is driven by `src/game/assets/manifest.ts`; treat this
  as the source of truth for assets loaded by Phaser.
- Static assets live in `public/assets/**`. Many sprites and audio files are
  generated by scripts under `tools/` and `scripts/`.
- DOM styling uses `src/app/globals.css`; this repo does not currently configure
  Tailwind.
- There are no tracked GitHub workflow files or conventional unit tests at the
  time this guidance was written.

## General review posture

- Prioritize correctness, user-visible regressions, asset/runtime mismatches,
  cleanup leaks, and verification gaps.
- Do not block on unrelated pre-existing issues unless the PR makes them worse
  or relies on them.
- Keep findings specific: cite the changed file and explain the runtime failure
  mode or maintenance risk.
- Avoid broad style preferences. Favor existing project patterns over new
  abstractions unless a change creates real duplication or unclear ownership.

## High-priority review areas

### Phaser lifecycle and cleanup

- Check that new scenes, timers, tweens, emitters, input handlers, audio, and
  display objects are destroyed or unsubscribed on shutdown/restart paths.
- `GameCanvas` dynamically imports Phaser and destroys the `Phaser.Game` on
  React unmount. PRs touching this boot path should preserve client-only loading
  and avoid server-side Phaser imports.
- `DungeonScene` has many persistent arrays and object references. Review
  restart/game-over changes for stale projectiles, enemies, pickups, tweens,
  and overlays that survive into a new run.

### Controls, docs, and in-game copy

- Runtime movement is WASD/arrow keys. Runtime shooting currently uses `SPACE`
  plus pointer/click firing; README text also mentions `J`, so only block on the
  mismatch for PRs that touch controls, docs, or in-game instructions.
- Start screen and how-to-play UI are Phaser-rendered with pointer zones and
  compact/tiny viewport branches. PRs changing this area should preserve button
  hit zones, close behavior, readable copy, and responsive placement.
- For DOM UI changes, check semantic elements and keyboard accessibility. For
  Phaser canvas UI, check pointer zones, keyboard/mouse affordances, visible
  feedback, and compact viewport behavior.

### Gameplay progression and balance

- Initial goblins come from `dungeon.enemyStarts`; additional goblins ramp with
  target enemy count. Brutes unlock via `BRUTE_UNLOCK_KILLS` or
  `BRUTE_UNLOCK_MS`, with a cap.
- `POWERUP_CONFIG` controls unlock gates, spawn weights, and presentation
  metadata. Duration and effect timing live in nearby constants and collection
  logic such as `QUICKSHOT_DURATION_MS`, `HASTE_DURATION_MS`,
  `WARD_DURATION_MS`, and `blastShotReady`.
- README documents regular ammo, heart pickups, quickshot, haste, ward, and
  blast. Code also contains seeker ammo/projectiles after progression
  thresholds. Keep review comments clear about README-documented behavior versus
  code-defined seeker behavior.
- Changes to enemy spawning, pickup selection, damage, hit stop, or scoring
  should be checked for runaway difficulty, impossible recovery, or resource
  starvation.

### Assets, manifests, and generated content

- Runtime audio source of truth is `assetManifest.audio` in
  `src/game/assets/manifest.ts`. `public/assets/audio/audio-manifest.json` is
  auxiliary and should stay consistent when touched.
- If a PR adds, removes, renames, or resizes runtime assets, require matching
  updates to manifests, metadata JSON, preloads, and README asset lists when
  those files are in scope.
- Sprite-sheet JSON dimensions and frame counts must match the loaded image and
  the frame sizes used by Phaser animations.
- Metadata/share-image changes in `src/app/layout.tsx` should stay in sync with
  `public/opengraph-image.png`, including dimensions and alt text.
- Generated asset changes should identify the tool or script used. Relevant
  commands include:
  - `npm run process:assets`
  - `npm run process:death-assets`
  - `npm run process:combat-juice`
  - `npm run generate:powerups`
  - `npm run generate:combat-assets`
  - `node tools/generate_audio_sfx.mjs`
  - `node scripts/generate-retro-soundtrack.mjs`
  - `python3 tools/process_corporate_goblin_assets.py`
  - `python3 tools/process_spreadsheet_brute_assets.py`

### Dependency and tooling checks

- `next lint` is not reliable for this repo because newer Next versions removed
  the old command path. Prefer `npm run build` and
  `npx tsc --noEmit --incremental false`.
- `npm run build` may rewrite `next-env.d.ts`; do not include that generated
  churn unless the PR intentionally changes Next type generation.
- Plain `npx tsc --noEmit` can create `tsconfig.tsbuildinfo` because incremental
  builds are enabled. Prefer `--incremental false` and remove the artifact if it
  appears.
- `npm ci` currently reports existing audit findings. Do not make a scoped
  gameplay/docs/config PR responsible for unrelated dependency hardening, but do
  block dependency PRs that worsen audit results or leave lockfiles inconsistent.
- Both `package-lock.json` and `pnpm-lock.yaml` are tracked. Dependency PRs
  should explain and verify the package-manager impact for both files when both
  are affected.

## Suggested verification by change type

- Config/docs only: `git diff --check origin/main...HEAD`.
- Source/gameplay/UI changes: `npm ci`, `npm run build`, and
  `npx tsc --noEmit --incremental false`.
- Asset manifest changes: run the relevant generator/processor when practical,
  then build and smoke-load the game.
- Dependency changes: install with the intended package manager, verify lockfile
  changes, run build/typecheck, and note any audit delta.
- Manual gameplay smoke checks when available: load `http://localhost:3000`,
  start a run, move with WASD/arrows, aim with pointer, fire with Space/click,
  collect ammo/powerups, toggle sound, open/close how-to-play, and restart after
  game over.

## Blocking threshold

Block when a change can break game boot, crash the scene, leak input/timers
across restarts, desynchronize runtime assets, make documented controls wrong
for the touched area, or ship without relevant verification for modified source
or dependency files.

Do not block for small copy/style improvements, unrelated existing README/code
mismatches, or missing manual smoke evidence when the PR is documentation-only
and local static checks are sufficient.
